# origin-prd-gen

## 当前环境变量及目录规则
- [PRD_DOC_URL] = 用户提供的 PRD 文档地址（分支 A 使用）
- [PRD_RAW_TEXT] = 用户在聊天里直接粘贴的 PRD 文本（分支 B 使用）
- [PRD_CHAT_IMAGES] = 用户在同一条聊天消息里附带的图片列表（分支 B 使用，仅做视觉读取，不落盘）
- [ORIGIN_PRD] = `.claude/docs/origin-prd.md`

## 数据源分流（必须先执行）

按以下优先级判定输入形态，命中即走对应分支，不再回退：

1. **分支 A（远端 URL）**：用户提供 [PRD_DOC_URL] → 用 `<DOC_PARSE_MCP>` 拉取并写入 [ORIGIN_PRD]。
2. **分支 B（聊天形态）**：用户在聊天里直接粘贴文本（[PRD_RAW_TEXT] 非空）和/或附带图片（[PRD_CHAT_IMAGES] 非空）→ 文本原样搬运、附件图用 vision 读出视觉描述（**不落盘**），合并写入 [ORIGIN_PRD]。
3. **同时给 URL 和聊天输入**：以 URL 为主体写入「原始需求搬运」段，聊天文本和图作为「补充说明」段追加，并在产物中明确标注两个来源。
4. **两者都没有**：必须立刻向用户索要（URL 或聊天文本+图至少一种），**禁止**凭经验补写。

## 目标
- **远端 URL（分支 A）**：基于 [PRD_DOC_URL]，使用 `<DOC_PARSE_MCP>` 拉取 PRD 内容，按原始章节顺序搬运有效需求到 [ORIGIN_PRD]，并过滤与当前前端页面实现无关的细节。
- **聊天形态（分支 B）**：把用户粘贴的文本原样搬运到 [ORIGIN_PRD] 的「原始需求搬运」段；用 vision 能力**直接读取**消息附件图，提取每张图的视觉描述（UI 元素、布局、关键文案、状态、粗略颜色），写入 [ORIGIN_PRD] 的「PRD 内嵌图视觉描述」段，**不把图片文件落盘到本地目录**。

## 核心约束

1. **数据源按分流走**：分支 A 不得凭经验改成 B，反之亦然。
2. **附件图只读不存**：分支 B 的附件图通过 vision 能力读取后，把视觉描述以文本形式落到 [ORIGIN_PRD]；**禁止**把原图文件保存到本地任何目录（避免上下文与磁盘冗余）。
3. 仅做原文/原图语义搬运与轻量清洗，不改变需求语义，不新增未出现的功能承诺。
4. 若信息不足，必须标注「待确认」，不得自行推断产品结论。
5. 每次写入必须带来源信息（章节段落线索 / 聊天图片在 PRD 文本中的位置或编号），保证可追溯。
6. 必须丢弃与当前前端页面实现无关的细节，至少包括：PRD 正文中对「识图」类能力的描述、`<EXCLUDED_DOMAIN_CATEGORIES>`（项目特定的与当前页面无关内容类别清单，详见 PLACEHOLDERS.md）相关需求与说明。
7. 不强制拆分为「功能需求/非功能需求」模板，仅按原始章节或聊天输入顺序组织内容。
8. 采用增量更新策略：已有内容不随意覆盖，优先追加「新增/变更」部分。
9. 一旦存在「待确认项」，必须主动告知用户并发起确认问题，在收到用户答复前不得将该项标记为已确认结论。
10. **章节标题必须以 markdown heading 形式落盘（强制，硬约束）**：原文档中所有章节标题（飞书 docx 的 H1/H2/H3 标题、聊天形态 PRD 自带的 `3.1.1` 等编号标题）落 [ORIGIN_PRD] 时**必须**写成 markdown heading 格式，**禁止**当普通段落行写。映射规则：
    - 顶级章节（飞书 H1 / 编号 `1` `2` 形式）→ `## ` heading
    - 二级章节（飞书 H2 / 编号 `1.1` `2.4` 形式）→ `### ` heading
    - 三级章节（飞书 H3 / 编号 `1.1.1` `8.10.2` 形式）→ `#### ` heading
    - 四级及更深 → `##### ` heading
    - 保留章节标题原文（含飞书章节编号），但 heading 前缀必须正确
    - 例：飞书原文「3.4 图像上传组件」H2 → 落盘为 `### 3.4 图像上传组件`；「8.10 发布流程」→ `### 8.10 发布流程`
    - **根因**：下游 step 0.5 PRD scope-narrower / xref-closure BFS 闭包扩展 / prd-clarifier §X.X 锚点核对 都依赖 markdown heading 结构识别章节边界；丢了 heading 等于把 PRD 退化成纯文本流，整个下游切片/引用闭包/对账机制失效（实测案例：2026-05-20 fresh-run origin-prd.md 5364 行平文，下游无法切片）
    - **Postcondition 自检（return 前必跑）**：Bash `grep -cE '^#{2,5}\s' [ORIGIN_PRD]` 必须 ≥ 5（PRD 至少 5 个章节标题）；< 5 → 自检 fail，**不允许 return**，必须回去把章节标题改成 markdown heading 重写 [ORIGIN_PRD]，再重新自检

## 输入检查

### 分支 A：远端 URL
0. **URL 预分类 + 解析后确认（强制，先于全量搬运 —— 治「抓错文档」）**：
   - 按路径段判 URL 类型：`/docx/{t}`→docx · `/sheets/{t}`→sheet · `/base/{t}`→bitable · `/slides/{t}`→slides · `/wiki/{node}`→wiki（**会自动解析到底层 obj_token + obj_type，底层文档可能与 URL 字面预期不符**）。
   - **wiki URL 高危**：实测 2026-05-20，用户给的某 wiki URL 解出的底层文档是「个人页UI优化 PRD」，而用户实际要的是另一篇 docx「世界卡创建流程」——wiki 节点指向的底层 doc 与用户口述需求不是一回事。
   - **拉取后必做一次匹配确认**：先只取文档**标题 + 顶层章节目录**（不做全量搬运），把「解析出的文档类型 + 标题」回报用户，确认它就是用户要搬运的那篇；标题/主题与用户口述需求明显不符（如要"世界卡创建流程"却解出"个人页UI优化"），或类型不符（要 docx 给了 sheet）→ **停下来问**，禁止凭 URL 盲搬错文档。确认通过后才进全量搬运。
1. 校验 [PRD_DOC_URL] 是否存在且可访问。
2. 使用 `<DOC_PARSE_MCP>` 拉取文档原始内容并确认非空。
3. 识别文档结构（标题、章节、小节、列表、表格、备注/注释）。
4. 识别并标记「无关细节」片段用于过滤。
5. 若 [ORIGIN_PRD] 不存在，先创建基础骨架。

### 分支 B：聊天形态
1. 提取用户最近一条消息中的 PRD 文本（[PRD_RAW_TEXT]）和附件图列表（[PRD_CHAT_IMAGES]）。
2. 文本部分：识别章节层级（如 PRD 自带的 `3.1.1`、`3.1.3` 等编号），保留原始顺序。
3. 附件图部分：用 vision 能力逐张读取，**不保存到本地任何目录**，只在记忆里提取视觉信息。
4. 若 [ORIGIN_PRD] 不存在，先创建基础骨架。

## 执行流程

### 分支 A（远端 URL）

1. **读取远端 PRD（大文档必须分页拉，防 socket 崩）**
   - 使用 `<DOC_PARSE_MCP>` 按 [PRD_DOC_URL] 获取文档内容。**大文档（>~800 行 / >50KB 或形态未知）禁止单次拉全文** —— 用 `offset`/`limit`（或 `has_more`）分页，每页拉回即按章节 Edit 写一小块（详见 `agents/_common/streaming-safety.md` §大文档读取）。实测：单次拉「世界卡创建流程」类大 PRD 连续撞 ~270s socket closed；分页 + 即写 + 断点续传才稳。
   - 保留章节层级与关键上下文，不打乱原始语义顺序。

2. **原始内容搬运与过滤**
   - 按原文章节顺序搬运需求内容，保留原始层级和上下文关系。
   - 过滤与当前前端页面实现无关的细节：图片内容识别、`<EXCLUDED_DOMAIN_CATEGORIES>` 及同类噪音信息。
   - 对表格或清单仅做等价转写，不做「功能/非功能」归类重组。

3. **与历史 ORIGIN_PRD 对齐**
   - 读取 [ORIGIN_PRD] 既有内容。
   - 识别「新增点/变更点/已存在点」：
     - 已存在且无变化：不重复写。
     - 同主题但内容更新：写入「变更记录」。
     - 全新需求：写入「新增需求」。

4. **写入 ORIGIN_PRD（大文件必须分块，防 socket 崩）**
   - 按「原始章节搬运」结构追加或更新对应段落。
   - 每个章节或关键条目补充来源定位（章节名或段落线索）。
   - **分块落盘（强制 —— 治大文档单次大 Write 崩 socket）**：长 PRD（实测「世界卡创建流程」类可达数千行）**禁止**一次 `Write` 整篇。流程：① 先 `Write` 文件骨架（标题 + 顶层 `## ` 章节占位）；② 再按章节用 `Edit` 逐块追加正文（每块 ≤ ~300 行 / 一个顶层章节为一块）。一次性大 Write 在长文档上会中断 socket、产物截断或丢 heading。分块后每块独立成功、可断点续写。
   - 分块写完后跑核心约束第 10 条的 Postcondition 自检（`grep -cE '^#{2,5}\s'` ≥ 5），不达标回去补 heading 重写。

5. **待确认项回传用户**

### 分支 B（聊天形态）

1. **文本部分搬运**
   - 把 [PRD_RAW_TEXT] 按原始顺序、原始层级写入 [ORIGIN_PRD] 的「原始需求搬运」段。
   - 保留 PRD 自带的章节编号（如 `3.1.1 新手引导`），不重新编号。
   - 应用「无关细节」过滤规则。

2. **附件图视觉读取（不落盘）**
   - 对 [PRD_CHAT_IMAGES] 中的每张图，用 vision 能力直接读取。
   - 每张图提取以下信息（按需补充，不强制全部）：
     - **图片在 PRD 文本中的引用位置**：如 `Image #3` 出现在 "3.1.3 第 2 步 toast" 上下文
     - **图类（推断）**：UI 截图 / 系统弹窗 / 流程示意图 / 设计稿草图 等
     - **核心 UI 元素**：标题、按钮、输入框、图标、徽章等可见元素与文案
     - **布局**：顶部/中部/底部 / 居中 / 贴边 / 浮层 / 模态等粗略位置关系
     - **状态**：默认态/选中态/错误态/空态/弹出态等
     - **颜色（粗略）**：主色调、关键反差色，**不要求精确 hex**（精确取色留给视觉分析阶段）

3. **写入 ORIGIN_PRD**
   - 「原始需求搬运」段写文本部分。
   - 「PRD 内嵌图视觉描述」段每张图一个二级条目，按聊天里出现的顺序排列。
   - 每个图条目末尾必须包含「关联 PRD 段落」，把该图与文本里对应的需求点链起来。

4. **与历史 ORIGIN_PRD 对齐**：同分支 A 第 3 步。

5. **待确认项回传用户**：含因图片不清晰/无法识别导致的描述不确定项。

## ORIGIN_PRD 推荐输出结构

```markdown
# ORIGIN_PRD

## 文档来源
- 数据源：<分支 A：[PRD_DOC_URL] | 分支 B：聊天文本 + N 张附件图 | 混合：URL + 聊天补充>
- 拉取方式：<DOC_PARSE_MCP> | 聊天直接读取 + vision 读图（不落盘）
- 最近同步时间：<YYYY-MM-DD HH:mm>
- （分支 B 时）附件图清单：Image #1, Image #2, ...（按聊天里出现顺序）

## 原始需求搬运
### <章节名 / 顺序号>
<原文搬运内容>

## PRD 内嵌图视觉描述（仅分支 B 或混合时存在）
### Image #N — <推断标题>
- 图类：<UI 截图 / 系统弹窗 / 示意图 ...>
- UI 元素：...
- 布局：...
- 状态：...
- 粗略颜色：...
- 关联 PRD 段落：<章节号 + 简述>

## 本次过滤明细
- 已过滤项：
  - 图片相关描述：...
  - `<EXCLUDED_DOMAIN_CATEGORIES>` 中各类相关内容：...
- 过滤原因：与当前前端页面实现无关

## 本次同步变更记录
- 新增：
  - ...
- 变更：
  - ...
- 删除/失效：
  - ...

## 待确认项
- Q-001 ...
- Q-002 ...
```

## 质量检查清单
- [ ] 已正确分流：分支 A / 分支 B / 混合，三者只能命中其一
- [ ] ORIGIN_PRD 内容与来源（URL 原文 / 聊天文本 / 附件图）语义一致，无主观扩写
- [ ] 内容按原文章节顺序或聊天输入顺序组织，未强制改写为功能/非功能模板
- [ ] 已过滤 `<EXCLUDED_DOMAIN_CATEGORIES>` 等与页面实现无关的细节
- [ ] 关键需求均包含来源线索（章节名、段落线索 或 图片编号 + 关联段落）
- [ ] 分支 B：所有附件图只在 [ORIGIN_PRD] 留下文本视觉描述，**未把图片文件保存到任何本地目录**
- [ ] 新增/变更已与历史 ORIGIN_PRD 做去重与对齐
- [ ] 输出结构完整，可直接被后续前端/技术方案技能消费

## 结束条件
- [ORIGIN_PRD] 已完成更新，覆盖本次 PRD 的有效需求并附带来源与变更记录。
- 待确认项已回传用户，未在用户答复前固化为结论。
