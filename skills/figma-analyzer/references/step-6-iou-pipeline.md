# Step 6: IoU 三阶段流水线（Phase 1 Flag → Phase 2 Tune → Phase 3 Finalize）

> 主 SKILL.md Step 6 的展开。何时 Read：开始 Step 6 IoU 匹配时。

## Step 6 入口：执行 IoU 匹配脚本

使用 IoU 算法将 Step 4 的视觉组件区域与 Figma 节点进行空间匹配：

```bash
cd scripts
python3 match_visual_to_figma.py \
  -s <截图路径> \
  -f <figma_raw.json路径> \
  -c <components.json路径> \
  --max-depth 4 \
  --save-data
```

This script:
1. **Applies coordinate scaling** to handle dimension differences between screenshot and Figma design
2. **Calculates IoU scores** for each visual component vs all Figma nodes
3. **Collects all candidates** with IoU ≥ 50% per visual component, then selects the highest-IoU node as the match
4. **Flags unmatched components** (Phase 1 of three-phase pipeline): any component with no candidate reaching IoU ≥ 50% is **flagged as `sub-50%`**, NOT yet removed. These flagged components remain in `match_data.pkl` and the report with explicit `🔴 IoU得分 < 50%` marker, awaiting Phase 2 (tune) and Phase 3 (finalize) decisions.
5. **Generates detailed report** with matching results and component relationships

> **Important**: Step 6 itself does NOT remove sub-50% components. Removal only happens in Phase 3 (finalize) after tuning attempts in Phase 2 fail.

**Key Improvement**: Unlike Step 5's name-based inference, this uses spatial matching which works even when Figma nodes have non-semantic names (e.g., "Frame 123456").

**Compatibility**: The `--config` parameter accepts `components.json` files generated by either this skill's Step 4 or the standalone `visual-screenshot-analyzer` skill. Both produce the same schema.

## 三阶段流水线

> **设计原因**：Step 6 单步执行后并不直接删除低 IoU 组件，因为低分往往是参数问题（max-depth 太浅 / 坐标原点偏移）而非真不存在。三阶段保证「先标记 → 再调优 → 最后裁定」的确定性流程，避免"边删边调"的不可重现行为。

### Phase 1: Flag（已在 Step 6 主脚本完成）

主脚本运行后产生：
- `match_data.pkl`：含全部组件（含 sub-50% 的 flagged 项）
- `visual_figma_match_report.txt`：sub-50% 组件用 `🔴 IoU得分 < 50%` 标记，但仍保留条目
- `components.json`：含全部组件条目

**Phase 1 退出态**：所有 sub-50% 组件被 flagged 但 **未删除**，进入 Phase 2。

---

### Phase 2: Tune（调优重试，必须在 Phase 3 前完成）

读取 `visual_figma_match_report.txt`，找出所有 `🔴 IoU得分 < 50%` 的组件，对这些组件执行以下两个 strategy：

**Strategy 1: depth escalation（max-depth 4 → 8, step=1）**

默认 `--max-depth 4` 可能遗漏层级较深的 Figma 节点。对低 IoU 组件，从 5 开始依次递增到 8，每次增加 1 后重新运行匹配，直到该组件 IoU ≥ 50% 或已尝试到 8 为止：

```bash
# 依次尝试 --max-depth 5、6、7、8
for depth in 5 6 7 8; do
  cd scripts
  python3 match_visual_to_figma.py \
    -s <截图路径> \
    -f <figma_raw.json路径> \
    -c <components.json路径> \
    --max-depth $depth \
    --save-data
  # 检查低 IoU 组件是否已改善，若全部 ≥ 50% 则提前停止
done
```

每次运行后检查之前 IoU < 50% 的组件是否提升到 ≥ 50%：
- ✅ 某组件在当前 depth 下 IoU ≥ 50%：该组件匹配成功，从 sub-50% flag 列表中移除（**仍不删除**，进入 Phase 3 决策）
- 若所有 sub-50% 组件在 `--max-depth 8` 后仍 < 50%，进入 Strategy 2

**Strategy 2: coordinate origin re-anchoring（坐标原点重锚定）**

Figma 的坐标体系中，节点的 `absoluteBoundingBox` 是相对于整个画布的绝对坐标，而不是相对于目标 Frame 的局部坐标。如果脚本的坐标原点计算有偏差，所有节点的坐标都会整体偏移，导致 IoU 普遍偏低。

检查方法：
1. 查看 `figma_raw.json` 中目标 Frame 节点的 `absoluteBoundingBox` (即 `x`、`y` 字段)
2. 确认脚本中是否使用了该 Frame 的 `x`、`y` 作为坐标偏移原点
3. 如果没有使用、或使用了错误的原点，修正脚本参数或手动指定偏移量后重新运行匹配

修正后若 sub-50% 组件分数达到 ≥ 50%，从 flag 列表中移除（仍不删除，进入 Phase 3 决策）。

**Phase 2 退出态**：
- 经过 Strategy 1 + Strategy 2 后，sub-50% 组件分为两类：
  - 类 A：调优后达标（IoU ≥ 50%）→ Phase 3 keep
  - 类 B：调优后仍 < 50% → Phase 3 drop
- **此时仍未真正删除任何文件**，只是分类。

---

### Phase 3: Finalize（最终裁定 + 真删除）

**仅在 Phase 2 完成后执行**。按 Phase 2 的分类执行：

- **类 A（调优达标）**：保留在 `components.json` / `match_data.pkl` / `visual_figma_match_report.txt`
- **类 B（调优仍失败）**：从所有产物中真正删除（参考下方 §"清理 components.json" / §"清理 visual_figma_match_report.txt"）
- **额外清理**：父节点已成为独立组件的子节点（与 Phase 2 调优正交，独立处理）

#### 额外清理：父节点已成为独立组件的子节点

在 Phase 3 执行 sub-50% 类 B 删除前后，独立执行「父节点已成为独立组件时的子节点」清理：

1. 读取 `visual_figma_match_report.txt`，找出所有 IoU ≥ 50% 的已匹配组件及其对应的 Figma 节点 ID
2. 对 `components.json` 中每个组件，检查其匹配的 Figma 节点是否上述已匹配节点的**后代子节点**（即祖先节点已被识别为独立组件）
3. 凡某其 Figma 祖先节点已成为独立组件 (IoU ≥ 50%) 的子节点，**无论其自身 IoU 得分多高，均视作不应拆分为独立组件**，将其从 `components.json` 和 `visual_figma_match_report.txt` 中删除
4. 输出说明：`已清理 Z 个父层已为独立组件的子节点`

#### 检查并清理 `components.json`

读取【产物目录】/`components.json`，找出所有需要被排除的低 IoU 组件（通过对照 `visual_figma_match_report.txt` 中标记为 `🔴 IoU得分 < 50%` 的组件名称），将这些组件从 `components.json` 中删除，并重新写回文件。

具体操作：
1. 读取 `visual_figma_match_report.txt`，提取所有被标记为 `🔴 IoU得分 < 50%，不作为独立组件` (已从产物中排除) 的组件名称列表
2. 读取 `components.json`，过滤掉上述名称对应的条目
3. 将过滤后的数组写回 `components.json`

#### 检查并清理 `visual_figma_match_report.txt`

`visual_figma_match_report.txt` 的报告内容中, IoU < 50% 的组件需要从报告中**完全删除**(不是标记)，具体操作：

1. 读取 `visual_figma_match_report.txt`，找出"一、匹配结果"部分中所有 `🔴 IoU得分 < 50%` 的组件条目，将这些条目整行删除（包括对应的⏎ 行及其相关说明行）
2. 找出"三、Figma节点语义标注"部分中所有对应的条目，将其整行删除
3. 将修改后的内容写回 `visual_figma_match_report.txt`

最终 `visual_figma_match_report.txt` 中应**只保留** IoU ≥ 50% 的组件相关内容，低 IoU 组件不得以任何形式（包括带 🔴 标记）出现在报告中。

#### 清理完成确认

完成上述检查和清理后，输出确认信息：
```
✅ IoU 检查完成：
- 调优成功（提升至 ≥ 50%）：A 个组件（通过增大 max-depth 或修正坐标原点）
- 父节点已为独立组件，清理子节点：Z 个
- components.json：保留 X 个组件，移除 Y 个（调优后仍 IoU < 50%）+ Z 个（父节点已为独立组件的子节点）
- visual_figma_match_report.txt：已删除对应条目（含匹配结果和语义标注部分）
```
